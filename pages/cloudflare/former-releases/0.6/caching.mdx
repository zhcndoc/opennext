## 缓存

`@opennextjs/cloudflare` 支持 [缓存](https://nextjs.org/docs/app/building-your-application/data-fetching/fetching-caching-and-revalidating#caching-data)。

### 如何启用缓存

`@opennextjs/cloudflare` 通过项目的 OpenNext 配置支持多种缓存机制。

#### 增量静态再生 (ISR)

增量缓存有两种存储选项可供选择。

- **Workers KV：** 一种 [快速](https://blog.cloudflare.com/faster-workers-kv) 存储，并使用 Cloudflare 的 [分层缓存](https://developers.cloudflare.com/cache/how-to/tiered-cache/) 来提高缓存命中率。当你将缓存数据写入 Workers KV 时，你写入的是任何 Cloudflare 位置都可以读取的存储。这意味着你的应用可以获取数据，将其缓存到 KV 中，然后随后来自世界各地的请求都可以从此缓存中读取。构建时的值由 [Workers Assets](https://developers.cloudflare.com/workers/static-assets/) 提供。定价信息可在 Cloudflare [文档](https://developers.cloudflare.com/workers/platform/pricing/#workers-kv) 中找到。
- **R2 对象存储：** 一种 [具有成本效益](https://developers.cloudflare.com/r2/pricing/) 的 S3 兼容对象存储选项，适用于大量非结构化数据。数据存储在单个区域，这意味着缓存交互可能较慢——这可以通过区域缓存来缓解。

<Callout>
  Workers KV 是最终一致的，这意味着当使用默认的 60 秒 TTL 时，更新可能需要长达 60 秒才能在全球范围内反映出来。
</Callout>

##### 1. 创建 KV 命名空间

```
npx wrangler@latest kv namespace create <YOUR_NAMESPACE_NAME>
```

##### 2. 将 KV 命名空间和服务绑定添加到你的 Worker

你的应用 worker 中使用的绑定名称是 `NEXT_INC_CACHE_KV`。
`WORKER_SELF_REFERENCE` 服务绑定应该是对你的 worker 的自引用，其中 `<WORKER_NAME>` 是你的 wrangler 配置文件中的名称。

```jsonc
// wrangler.jsonc
{
  // ...
  "name": "<WORKER_NAME>",
  "kv_namespaces": [
    {
      "binding": "NEXT_INC_CACHE_KV",
      "id": "<BINDING_ID>",
    },
  ],
  "services": [
    {
      "binding": "WORKER_SELF_REFERENCE",
      "service": "<WORKER_NAME>",
    },
  ],
}
```

##### 3. 配置缓存

在你的项目 OpenNext 配置中，启用 KV 缓存。

```ts
// open-next.config.ts
import { defineCloudflareConfig } from "@opennextjs/cloudflare";
import kvIncrementalCache from "@opennextjs/cloudflare/overrides/incremental-cache/kv-incremental-cache";
// ...

export default defineCloudflareConfig({
  incrementalCache: kvIncrementalCache,
  // ...
});
```

##### 1. 创建 R2 存储桶

```
npx wrangler@latest r2 bucket create <YOUR_BUCKET_NAME>
```

##### 2. 将 R2 存储桶和服务绑定添加到你的 Worker

你的应用 worker 中使用的绑定名称是 `NEXT_INC_CACHE_R2_BUCKET`。服务绑定应该是对你的 worker 的自引用，其中 `<WORKER_NAME>` 是你的 wrangler 配置文件中的名称。

R2 存储桶使用的前缀可以通过 `NEXT_INC_CACHE_R2_PREFIX` 环境变量配置，默认为 `incremental-cache`。

```jsonc
// wrangler.jsonc
{
  // ...
  "name": "<WORKER_NAME>",
  "r2_buckets": [
    {
      "binding": "NEXT_INC_CACHE_R2_BUCKET",
      "bucket_name": "<BUCKET_NAME>",
      "preview_bucket_name": "<PREVIEW_BUCKET_NAME>",
    },
  ],
  "services": [
    {
      "binding": "WORKER_SELF_REFERENCE",
      "service": "<WORKER_NAME>",
    },
  ],
}
```

##### 3. 配置缓存

在你的项目 OpenNext 配置中，启用 R2 缓存。

你可以选择设置一个区域缓存与 R2 增量缓存一起使用。这将启用更快的缓存条目检索，并减少发送到对象存储的请求量。

区域缓存有两种模式：

- `short-lived`：响应最多可重用一分钟。
- `long-lived`：获取响应被重用直到重新验证，ISR/SSG 响应最多可重用 30 分钟。

此外，可以通过 `shouldLazilyUpdateOnCacheHit` 选项启用区域缓存的延迟更新。当从缓存请求数据时，它会向 R2 存储桶发送后台请求以获取最新条目。这在 `long-lived` 模式下默认启用。

```ts
// open-next.config.ts
import { defineCloudflareConfig } from "@opennextjs/cloudflare";
import r2IncrementalCache from "@opennextjs/cloudflare/overrides/incremental-cache/r2-incremental-cache";
import { withRegionalCache } from "@opennextjs/cloudflare/overrides/incremental-cache/regional-cache";
// ...

// 启用区域缓存时：
export default defineCloudflareConfig({
  incrementalCache: withRegionalCache(r2IncrementalCache, {
    mode: "long-lived",
    shouldLazilyUpdateOnCacheHit: true,
  }),
  // ...
});

// 不使用区域缓存：
export default defineCloudflareConfig({
  incrementalCache: r2IncrementalCache,
  // ...
});
```

##### 4. 配置队列

在你的项目 OpenNext 配置中，启用缓存并设置队列。

Durable Object 队列将在需要时向页面发送重新验证请求，并提供请求去重支持。
默认情况下，最多会有 10 个 Durable Object 队列实例，它们每个可以并行处理最多 5 个请求，最多支持 50 个并发 ISR 重新验证。

```ts
// open-next.config.ts
import { defineCloudflareConfig } from "@opennextjs/cloudflare";
// ...
import doQueue from "@opennextjs/cloudflare/overrides/queue/do-queue";

export default defineCloudflareConfig({
  // ...
  queue: doQueue,
});
```

你还需要在 `wrangler.jsonc` 文件中添加一些绑定。

```jsonc
"durable_objects": {
    "bindings": [
      {
        "name": "NEXT_CACHE_DO_QUEUE",
        "class_name": "DurableObjectQueueHandler"
      }
    ]
  },
  "migrations": [
    {
      "tag": "v1",
      "new_sqlite_classes": ["DurableObjectQueueHandler"]
    }
  ],
```

你可以使用环境变量自定义队列的行为：

- 一个 durable object 实例同时可以处理的最大重新验证数量 (`NEXT_CACHE_DO_QUEUE_MAX_REVALIDATION`)
- 重新验证在被视为失败之前可以花费的最大时间（毫秒） (`NEXT_CACHE_DO_QUEUE_REVALIDATION_TIMEOUT_MS`)
- 如果重新验证失败，再次尝试重新验证的时间间隔。如果再次失败，它将指数退避直到达到最大重试间隔 (`NEXT_CACHE_DO_QUEUE_RETRY_INTERVAL_MS`)
- 重新验证路径可以尝试的最大次数 (`NEXT_CACHE_DO_QUEUE_MAX_NUM_REVALIDATIONS`)
- 禁用此 durable object 的 SQLite。仅当你的增量缓存不是最终一致时才应使用它 (`NEXT_CACHE_DO_QUEUE_DISABLE_SQLITE`)

<Callout>
  队列还有 2 种额外模式可供使用：`direct` 和内存队列

- 内存队列将去重请求，但仅基于每个 isolate。它不完全适合生产部署，你可以自担风险使用它！

- 队列的 `direct` 模式旨在用于调试目的，不建议在生产中使用。它仅在预览模式下工作（即 `wrangler dev`）

  对于使用 Page Router 的应用，`res.revalidate` 需要提供名为 `WORKER_SELF_REFERENCE` 的自引用服务绑定。

</Callout>

#### 按需重新验证

标签重新验证机制可以使用 [Cloudflare D1](https://developers.cloudflare.com/d1/) 数据库或带有 `SqliteStorage` 的 [Durable Objects](https://developers.cloudflare.com/durable-objects/) 作为其后端存储，用于存储有关标签、路径和重新验证时间的信息。

要使用按需重新验证，你还应该遵循 [ISR 设置步骤](#incremental-static-regeneration-isr)。

<Callout>
  如果你的应用 **仅** 使用 pages router，则不需要标签缓存，应跳过此步骤。
  如果你的应用不使用 `revalidateTag` 也不使用 `revalidatePath`，你也可以跳过此步骤。
</Callout>

标签缓存有 3 种不同的选项可供选择：`d1NextTagCache`、`doShardedTagCache` 和 `d1TagCache`。
选择哪一个应基于两个关键因素：

1. **预期负载**：考虑你预期的流量或数据量。
2. **`revalidateTag` / `revalidatePath` 的使用**：评估这些功能将被使用的频率。

如果其中任何一个因素很重要，建议选择分片数据库。此外，结合区域缓存可以进一步增强性能。

##### 2. 配置缓存

在你的项目 OpenNext 配置中，启用 KV 缓存并设置队列。队列将在需要时向页面发送重新验证请求，但不会去重请求。

```ts
// open-next.config.ts
import { defineCloudflareConfig } from "@opennextjs/cloudflare";
import kvIncrementalCache from "@opennextjs/cloudflare/overrides/incremental-cache/kv-incremental-cache";
import memoryQueue from "@opennextjs/cloudflare/overrides/queue/do-queue";
import doShardedTagCache from "@opennextjs/cloudflare/overrides/tag-cache/do-sharded-tag-cache";

export default defineCloudflareConfig({
  incrementalCache: kvIncrementalCache,
  tagCache: doShardedTagCache({ baseShardSize: 12, regionalCache: true }),
  queue: memoryQueue,
});
```

doShardedTagCache 接受以下选项：

- `baseShardSize` - 用于缓存的分片数量。你拥有的分片越多，缓存将越均匀地分布在各个分片上。默认值为 4。Soft（用于 `revalidatePath` 的内部 next 标签）和 hard 标签（你在应用中定义的标签）将被拆分到不同的分片中
- `regionalCache` - 是否为缓存使用区域缓存。默认值为 false。当你想减少 durable object 的压力时，此选项很有用
- `regionalCacheTtlSec` - 区域缓存的 TTL。默认值为 5 秒。增加此值将增加缓存跨区域失效所需的时间
- `enableShardReplication`：启用复制分片。分片复制将把每个分片复制为副本，以进一步分散负载
- `shardReplicationOptions.numberOfSoftReplicas`：soft 标签分片的副本数量
- `shardReplicationOptions.numberOfHardReplicas`：hard 标签分片的副本数量
- `maxWriteRetries`：写入标签时执行的重试次数

##### 3. 在部署期间初始化缓存

为了使缓存正确初始化构建时的重新验证数据，你需要作为部署步骤的一部分运行一个命令。这应作为每次部署的一部分运行，以确保缓存填充了每个构建的数据。

要同时填充远程绑定并部署你的应用，你可以使用 `deploy` 命令。同样，`preview` 命令将填充你的本地绑定并启动 Wrangler 开发服务器。

```sh
# 填充远程并部署。
opennextjs-cloudflare deploy

# 填充本地并启动开发服务器。
opennextjs-cloudflare preview
```

可以使用 `populateCache` 命令仅填充缓存而不执行任何其他步骤。

```sh
# 目标作为选项传递，要么是 `local` 要么是 `remote`。
opennextjs-cloudflare populateCache local
```
